**Status:** Initial living `/speckit.specify` prompt; not a completed Spec Kit specification.  
**Release:** MVP · **Phase:** Runnable foundation and tenant security  
**Prerequisites:** GOZ-0003

## Starting prompt for `/speckit.specify`

Build **Scoped RBAC permission foundation** as one bounded, runnable, tested vertical slice of the open-source **Gözleme** federated AI capability registry.

**User-visible outcome:** Assign a role and watch privileged operation be denied then permitted.

**In scope:** Built-in roles, org membership permissions, action/resource contract.

**Important boundary:** Full policy evaluator comes later.

Respect the authoritative `docs/architecture/architecture-baseline.md`, `docs/architecture/security-invariants.md`, `docs/decisions/consistency-review.md`, `.gozleme/manifest.yaml`, and spec registry. Use the already installed Spec Kit workflow, its native templates, and confirmed architecture decisions. Do not re-create Spec Kit templates or reinstall Spec Kit. Do not claim unimplemented post-MVP security guarantees.

### Required behavior and acceptance tests

- Deliver the outcome above through the cumulative running Next.js/.NET 10/PostgreSQL application; include positive and negative tests suitable for this feature.
- Preserve organization isolation and private visibility, using existing policy/RLS boundaries. Never reveal confidential metadata or secrets through UI, APIs, search indexes, logs, or screenshots.
- Include reproducible seeded fixtures, exact demo commands, expected UI/API observations, and automatic browser-driven demo evidence when feasible.
- Capture meaningful actual screenshots from the working implementation (or API/log evidence if no useful UI view), with PR links and sanitized synthetic data.
- Keep existing demos and smoke tests working. Compose remains runnable without cloud services, hosted embedding providers, or external identity providers by default.
- Document contracts, storage migrations, compatibility and dependency impacts, and any unsupported modes explicitly.
- Implement only this bounded slice. Defer unrelated subfeatures to their scheduled specs rather than constructing speculative frameworks.

### Organization and tenancy conventions (GOZ-0002-IF-01, IF-05, IF-06, IF-07, IF-08, 2026-11-15)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0002 at commit `f95be4c` (code as demonstrated at `8a9941e`; findings in `docs/specs/002-organizations/reviews/impact-findings.json`). These bullets record implemented organization facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants._

- (IF-05) Tenants are rows of `gozleme.organizations` (`id` uuid UUIDv7, permanent; `display_name` 1–100 chars, **not unique**; no handle, slug, hierarchy, lifecycle or deletion). Membership is a row in `gozleme.memberships` (PK `organization_id, user_id`). It has no role column, and removal deletes the row. An organization-scoped API is mapped under `/api/v1/organizations/{organizationId}/…` with the ID in the path, never taken implicitly from an "active" organization. Its first step is the membership check `OrganizationAccess.FindMembershipAsync` (`src/Gozleme.Api/Organizations/OrganizationAccess.cs:17-25`), or the GOZ-0003/GOZ-0004 successor of that check, read from the database on every request. A malformed ID, an unknown organization and a non-member all get the same empty `404` with `Cache-Control: no-store` (`OrganizationEndpoints.cs:24,45-49`). `activeOrganizationId` from `GET /api/v1/organizations` (`memberships.selected_at`) is a UI preference only and never authority. Web pages for organization data live under `/organizations/[organizationId]/…`, render the existing "Organization not found" page on 404, and build API paths with `segment()` (`web/src/lib/organizations.ts:44`), which neutralises dot segments. A new tenant-owned table carries `organization_id uuid NOT NULL` with a foreign key to `organizations(id)`.
- (IF-01) Until GOZ-0003 merges, tenant isolation is enforced **by application authorization only**: no RLS policy exists on `organizations`, `memberships` or `invitations` (GOZ-0002 plan, Complexity Tracking). Do not claim RLS protection for any data before GOZ-0003 is merged and verified.

Organization display names, emails and invitation codes never appear in spans, metrics, logs or URLs. Security audit event IDs are allocated per module: identity uses 1001–1010 and organizations use 1101–1108 (`src/Gozleme.Api/Identity/SecurityAudit.cs:13-65`). Give a new module its own range. Audit events remain log records only.
- (IF-08) A new rate-limited endpoint must attach `RateLimitedOperation` metadata (`src/Gozleme.Api/Identity/IdentityServiceCollectionExtensions.cs:119-129,163`; pattern `OrganizationEndpoints.cs:38-41`). Without it, the shared `OnRejected` handler records the rejection as a `gozleme.auth` sign-in or register failure. Rate limiters are in memory and per API instance. Partition by account ID when the endpoint requires a session.
- (IF-06) Demo state after the GOZ-0002 suite:

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0002 at commit `f95be4c` (code as demonstrated at `8a9941e`; findings in `docs/specs/002-organizations/reviews/impact-findings.json`). These bullets record implemented organization facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants._

- (IF-03) **Replace the interim role-neutral rule.** Today any member may rename, invite, list and revoke invitations, list members, remove any other member, and leave. Only the last member is protected (spec FR-015/FR-016; `OrganizationEndpoints.cs`). Every organization-scoped handler calls `OrganizationAccess.FindMembershipAsync` first, so that is the single place to evolve:
  - Keep the membership check first. Non-members still get the identical empty 404.
  - Put the permission check after it. A member who lacks a permission may get `403 {"error":"forbidden"}`, which is already in the contract's error enum (`docs/specs/002-organizations/contracts/organizations-api.openapi.yaml:52`) but is unused today.
  - Turn the last-member guard into a guard that always keeps at least one member able to manage membership. Run it under the same `organizations` row lock (`OrganizationEndpoints.cs:173,190`), including when roles change.
  - Add a bounded `forbidden` failure category to `gozleme.org.operations` (`OrganizationTelemetry.cs:43-51`).
  - Keep `OrgOperation` names as the starting action vocabulary.
- (IF-03) Existing organizations have no roles. `joined_via = 'creator'` and `organizations.created_by` grant nothing by FR-018, and the creator may already have been removed (`OrganizationBoundaryTests.cs`, `Extra_privilege_fields_are_ignored_and_the_creator_has_no_special_standing`). Choose the migration rule that assigns initial roles to existing members, for example every current member becomes a manager or only creators do, during this spec's clarification **with the maintainer**. Do not infer it. The rule must be additive and safe for the Helm `pre-upgrade` migration.
- (IF-04) GOZ-0002 already revokes the departing account's open invitations when a member is removed or leaves (maintainer decision on GOZ-0002-IF-04; FR-015). It does this in the removal transaction under the organization row lock, sets `revoked_by` to the acting member, and writes audit 1104 for each revoked invitation (`OrganizationEndpoints.cs` `RemoveMemberAsync`; test `MembershipTests.Removing_or_leaving_revokes_the_departing_accounts_open_invitations`). Build on this rather than re-implementing it:
  - Keep that behaviour, and its test, when removal becomes a permissioned action.
  - Decide who may create and revoke invitations.
  - Decide whether losing the invitation-creating permission through a role change should also revoke that account's open invitations, and test the choice.
- (IF-09) Narrow GOZ-0002's no-delegation boundary deliberately:
  - `OrganizationBoundaryTests.No_role_owner_admin_or_permission_column_exists` pins the exact column list of the three organization tables and forbids `role|owner|admin|permission|delegat` (`OrganizationBoundaryTests.cs:32`).
  - `Delegation_routes_do_not_exist` asserts 404/405 for `/members/{user}`, `/members/{user}/role`, `/transfer`, `/owner`, `/admins`, `/roles` and `DELETE` on the organization (`:42-52`).
  - The e2e boundary test forbids role, admin and owner wording on the organization page and allows exactly one combobox (`e2e/tests/organizations-demo.spec.ts:276-277`).
  - Keep ownership transfer, organization deletion and delegated administration absent, because they are post-MVP (R3-08, R3-24).
- (IF-13) No quota or rate limit applies to creating organizations or invitations, and the organization, member and invitation lists are not paged. If invitation creation becomes a permission, say so. Do not add paging unless this spec needs it.
- (IF-14) Assign roles only to existing members, selected by their opaque `userId` from the member list. Do not assign by email address: GOZ-0002 FR-013 forbids any lookup that reveals whether an account exists, and emails are unverified.
- (IF-15) Today any member can mint an invitation and admit a second account they control. Reviewer, approver and manager capabilities must come from explicit role grants, never from membership alone.

### Tenant RLS conventions (GOZ-0003-IF-01, IF-02, IF-09, IF-10, IF-19, 2026-11-15; IF-19 added 2026-11-16)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0003 at commit `9131bda` (code as demonstrated at `424a15e`; findings in `docs/specs/003-tenant-rls/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 4 → 5. These bullets record implemented tenant-RLS facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants. Items that would change them are routed to the maintainer as GOZ-0003 human decisions and are not decided here._

- (IF-01) Once GOZ-0003 has merged (verify on `main`), organization data is protected by the application membership check **and** PostgreSQL row-level security, enabled and **forced** (binding the owner login too) on `organizations`, `memberships` and `invitations`. This supersedes the GOZ-0002-IF-01 "application authorization only" bullet above. The database contract is `docs/specs/003-tenant-rls/contracts/tenant-context.md`, and migration `src/Gozleme.Api/Persistence/Migrations/20261117000000_TenantRls.cs` is the model. A new tenant-owned table must, **in its creating migration**:
  - carry `organization_id uuid NOT NULL` referencing `gozleme.organizations(id)`;
  - `ENABLE` and `FORCE ROW LEVEL SECURITY`, with one policy per command of the shape `CASE WHEN gozleme.rls_internal() THEN true ELSE organization_id IN (SELECT gozleme.account_organizations()) END` (contract §5; `CASE` fixes evaluation order);
  - be added to `TableClassification.TenantOwned` (`src/Gozleme.Api/Persistence/TableClassification.cs`);
  - be added to the cross-tenant matrix in `tests/Gozleme.Api.IntegrationTests/RlsIsolationTests.cs` for both the `app` and `owner` roles (fixtures `Infrastructure/TwoTenants.cs`; leak queries via `GozlemeDatabase.InTransactionAsync` with `GozlemeDatabase.Establish(GozlemeDatabase.SignContext(...))`). `RlsCatalogTests` checks only that a policy exists, not what it admits.
- (IF-01) `RlsCatalogTests` (`RlsCatalog.ViolationsAsync`) fails on an unclassified `gozleme` table, a tenant table without enabled or forced RLS or without a policy, any `SharedPublic` entry (reserved until GOZ-0012), a `SECURITY DEFINER` function in `gozleme` outside the pinned `TableClassification.DefinerHelpers` or a migrator-owned one in any other non-system schema, any view, materialized view or foreign table in `gozleme` (both added at `a81e54e`, GOZ-0003-IF-12), and any `gozleme`/`gozleme_private` function executable by `PUBLIC`. PostgreSQL grants `EXECUTE` to `PUBLIC` on every new function by default, so each new function (trigger functions included) needs `REVOKE EXECUTE … FROM PUBLIC` and an explicit grant to `gozleme_app` if it is called. Do not add `SECURITY DEFINER` functions: inside any migrator-owned definer function `gozleme.rls_internal()` is true, so it bypasses every tenant policy. Extending the pinned list is a security-review item.
- (IF-19) Row policies cannot compare old and new rows. Some tables have identity, tenant-key or lifecycle columns that may change in one direction only: set once, expiry only earlier, never reopened, never moved to another organization. Each such table needs a `BEFORE UPDATE` guard trigger as well as its policies. The model is `gozleme.invitations_guard` in `20261117000000_TenantRls.cs`:
  - Write it as plain `plpgsql`, never `SECURITY DEFINER`, with a fixed `search_path` and `PUBLIC` execute revoked. A trigger function needs no grant to `gozleme_app`.
  - Raise `insufficient_privilege` (`42501`), so that `TenantTransaction` answers the empty 404.
  - Keep `organization_id` immutable on every tenant table.
  - Restrict a policy's bearer-capability branch (such as the invitation code) in its `USING` clause to the open state. A `WITH CHECK` clause sees only the new row.
  - A guard binds every role, the owner and superusers included. A cascaded `ON DELETE SET NULL` fires it, so allow that change explicitly.
  - The catalog check does not pin triggers, so prove each guard with a behavioural test (pattern `TenantContextBoundaryTests.An_invitation_code_cannot_move_reopen_or_extend_its_invitation`).
  - Fully immutable tables still follow GOZ-0000-IF-04 (revoke `UPDATE`/`DELETE`).
- (IF-01) Pins to update with each migration: `LATEST_MIGRATION` in `e2e/tests/bootstrap-demo.spec.ts` (now `/_TenantRls$/`); `BootstrapBoundaryTests.Gozleme_schema_holds_exactly_the_identity_and_organization_tables`; and `BootstrapBoundaryTests.Only_migration_history_and_the_context_key_tables_exist_outside_system_schemas`, which allows only `gozleme_private.context_keys` and `public.__EFMigrationsHistory` outside `gozleme`.
- (IF-02) Request transaction model: `TenantTransaction` (`src/Gozleme.Api/Tenancy/TenantTransaction.cs`) is an endpoint filter attached only to the `/organizations` and `/invitations` route groups (`OrganizationEndpoints.cs:28,42`).
  - Endpoints mapped under `/api/v1/organizations/{organizationId}/…` get it automatically. An endpoint on any other group that touches tenant data must add `.AddEndpointFilter<TenantTransaction>()`; without it every tenant query returns nothing (fail closed).
  - Inside the filter, use the ambient transaction: do not call `BeginTransactionAsync`, do not read tenant data through `IDbContextFactory` or a second `DbContext` (it has no context), and defer audit records with `TenantTransaction.AfterCommit`.
  - The signed context (`v1.<account>.<expires>.<hmac>`, 5 minutes) names the session's account (`ClaimTypes.NameIdentifier`) only, never an organization or role, and every statement re-reads membership. Removal therefore takes effect on the next statement.
  - The filter holds one transaction and one pooled connection for the whole handler. Do not do network or long-running I/O inside it (object storage, embedding providers, federation peers, sandboxes). Split such work into short explicit transactions, each starting with `TenantContext.EstablishAsync(db, signer.Sign(accountId), ct)`. `now()` is the transaction start time, so a token is never re-expired inside one transaction.
  - A principal that is not a signed-in account (a background worker, scheduled job, sync applier or federation peer) touches tenant rows only through a second signed token kind. That token names one organization and a bounded purpose, is verified in the database with the same context key, and is admitted by a new policy branch that the catalog check pins (maintainer decision 2026-11-16, GOZ-0003-IF-04, option A; first consumer GOZ-0015). This is the only sanctioned path: never add a `BYPASSRLS` role, a definer helper or a member service account for it. The first consuming spec designs the token format, the purpose vocabulary, which process signs, and how the catalog pins the branch. Anonymous discovery is not covered by this decision and remains GOZ-0012's question (GOZ-0001-IF-22).
  - Under FORCE, a migration running as the owner without a context sees no tenant rows, so a data migration (`UPDATE`/`DELETE`/`INSERT … SELECT`) on tenant tables silently changes **zero** rows. DDL (`ADD COLUMN … DEFAULT …`) is unaffected. Maintainer decision 2026-11-16 (GOZ-0003-IF-03, option A): a reviewed migration may lift the owner binding **only inside its own transaction**, either with the transaction-local `gozleme.rls_helper` flag or with `ALTER TABLE … NO FORCE ROW LEVEL SECURITY` and then `FORCE` again before commit. A superuser test must assert the per-row results. A migration may **never** disable a guard trigger (IF-19): guarded columns are not backfilled, and a needed change extends the guard in a new migration.
- (IF-09) Telemetry and audit:
  - The `gozleme.tenant.transaction` span (events `gozleme.tenant.context.established` and `gozleme.tenant.context.cleared`) is the parent of module spans and carries no organization ID. `gozleme.organization.id` stays a span attribute, set only after membership is confirmed and never used as a metric label (maintainer decision, GOZ-0003).
  - `gozleme.tenant.denials` has the single label `gozleme.tenant.denial.reason` ∈ {`missing`, `invalid`, `expired`, `refused_write`}. Adding a reason is a contract change.
  - Audit ranges in use: identity 1001–1010, organizations 1101–1108, tenancy 1201–1210 (`src/Gozleme.Api/Identity/SecurityAudit.cs`). Give a new module the next free range, from 1301.
  - The filter answers any SQLSTATE `42501` with the empty 404, counts `refused_write` and writes audit 1202. This includes a plain `permission denied` from a missing grant, so in development a 404 with `refused_write` usually means a missing `GRANT` or policy.
  - An `UPDATE` or `DELETE` whose target the `USING` clause hides changes zero rows without error. EF then raises `DbUpdateConcurrencyException`, answered as 500. Authorization must never rely on RLS errors; the application check runs first.
  - Never log or trace the signed context (prefix `v1.`), the key or an invitation code hash. Pass them only as SQL parameters. The demo scans captured telemetry for them.

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0003 at commit `9131bda` (code as demonstrated at `424a15e`; findings in `docs/specs/003-tenant-rls/reviews/impact-findings.json`). - (IF-05) Row-level rules are member-level, which is coarser than roles (GOZ-0003 research R7):
  - any member may `INSERT` memberships into its organization (`seed` uses this; the API exposes no such path), `DELETE` any membership in it, and insert, update or delete its invitations;
  - `memberships` `UPDATE` is admitted only for the account's **own** row (`user_id = current_account_id()`, migration `20261117000000_TenantRls.cs:198-202`), which is what `selected_at` needs.

  So if one member changes another member's role in a `memberships` column, RLS filters the update out silently: zero rows change, and EF raises `DbUpdateConcurrencyException`, answered as 500. RLS never refuses it. In this spec's migration, decide and test:
  1. where a role lives: a column on `memberships`, or a new tenant-owned table that follows the GOZ-0003-IF-01 rules;
  2. the policy change that lets an authorized member change another member's role;
  3. whether RLS stays member-level, with roles enforced only by the application (the documented GOZ-0003 posture), or also narrows writes by role.

  Keep the application membership check first and the RLS layer independent. Extend `RlsIsolationTests`, `OrganizationBoundaryTests` and `TenantSeedTests`. `seed` must give the fixed members their roles while acting as a seeded member.
- (IF-03) **Initial-role backfill hazard.** The initial-role rule this spec must choose with the maintainer (GOZ-0002-IF-03) cannot be applied by a plain data migration:
  - Under FORCE the migrator login sees no tenant rows without a valid context, so `UPDATE gozleme.memberships SET … WHERE …` succeeds while changing **zero** rows.
  - A signed account context cannot enumerate other tenants.
  - On a fresh database the key is provisioned only after migrations run (`MigrationRunner.cs`).

  Maintainer decision 2026-11-16 (GOZ-0003-IF-03, option A): this reviewed migration may lift the owner binding only inside its own transaction, using the transaction-local `gozleme.rls_helper` flag or `NO FORCE` and then `FORCE`. A superuser test must assert the per-row results of the initial-role rule, and the migration may never disable a guard trigger. The initial-role rule itself is still chosen with the maintainer during clarification (GOZ-0002-IF-03).

  One case is open: if this spec adds a guard for the role column (IF-19), the decision does not say whether populating that column in the same migration, before the guard is created, counts as backfilling a guarded column. Confirm it with the maintainer during clarification before relying on that order.

### Implementation alignment (GOZ-0003-IF-19, 2026-11-16)

_Provenance: added by the GOZ-0003 Spec Impact Analyst on re-analysis at `a0421c0` (second convergence pass, fix `9373c0f`; findings in `docs/specs/003-tenant-rls/reviews/impact-findings.json`). - (IF-19) `memberships` has no guard trigger, and its `UPDATE` policy admits the account's **own** row. At the database layer a member can therefore rewrite its own `joined_via`, `joined_at` and `invitation_id`. If roles become a `memberships` column, it could also raise its own role. The API exposes neither, so this matters only for injected SQL, but RLS is meant to be an independent layer. In this spec's migration:
  - keep `organization_id` and `user_id` fixed;
  - make a role change impossible through the own-row branch, using a guard trigger or a policy that excludes the role column;
  - do not base the initial-role rule (GOZ-0002-IF-03) on `joined_via = 'creator'` unless that column is guarded first. Seeded memberships also use `joined_via = 'invitation'` with no invitation (`OperatorCommands.cs` `AddMembers`).

  Test each of these as `gozleme_app` with a valid context.
