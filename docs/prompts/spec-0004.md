# GOZ-0004 — Scoped RBAC permission foundation

**Status:** Initial living `/speckit.specify` prompt; not a completed Spec Kit specification.  
**Release:** MVP · **Phase:** Runnable foundation and tenant security  
**Prerequisites:** GOZ-0003

## Starting prompt for `/speckit.specify`

Build **Scoped RBAC permission foundation** as one bounded, runnable, tested vertical slice of the open-source **Gözleme** federated AI capability registry.

**User-visible outcome:** Assign a role and watch privileged operation be denied then permitted.

**In scope:** Built-in roles, org membership permissions, action/resource contract.

**Important boundary:** Full policy evaluator comes later.

Respect the authoritative `docs/architecture/architecture-baseline.md`, `docs/architecture/security-invariants.md`, `docs/decisions/consistency-review.md`, `.gozleme/manifest.yaml`, and spec registry. Use the already installed Spec Kit workflow, its native templates, and confirmed architecture decisions. Do not re-create Spec Kit templates or reinstall Spec Kit. Do not claim unimplemented post-MVP security guarantees.

### Required behavior and acceptance tests

- Deliver the outcome above through the cumulative running Next.js/.NET 10/PostgreSQL application; include positive and negative tests suitable for this feature.
- Preserve organization isolation and private visibility, using existing policy/RLS boundaries. Never reveal confidential metadata or secrets through UI, APIs, search indexes, logs, or screenshots.
- Include reproducible seeded fixtures, exact demo commands, expected UI/API observations, and automatic browser-driven demo evidence when feasible.
- Capture meaningful actual screenshots from the working implementation (or API/log evidence if no useful UI view), with PR links and sanitized synthetic data.
- Keep existing demos and smoke tests working. Compose remains runnable without cloud services, hosted embedding providers, or external identity providers by default.
- Document contracts, storage migrations, compatibility and dependency impacts, and any unsupported modes explicitly.
- Implement only this bounded slice. Defer unrelated subfeatures to their scheduled specs rather than constructing speculative frameworks.

### Delivery governance

- Work exclusively on `chore/*`, `feature/*`, or `bugfix/*` branch; never push to `main`, merge any PR, or enable auto-merge.
- `drive-speckit` coordinates specify → plan → tasks → implementation → automated demo → converge → post-convergence Spec Impact Analyst → Roadmap Steward update → PR-ready state.
- Update per-spec `progress.yaml` when Spec Kit creates a working directory, update `.gozleme/spec-registry.yaml`, regenerate `docs/roadmap/spec-register.md` and attach evidence.
- Automatically align **future unimplemented** prompt files with verified implementation findings within approved architecture; seek human approval for changes to confirmed decisions, security guarantees, or committed MVP scope.
- Human maintainer alone approves and merges PRs. No claim of completion on `main` until merge is independently verified.

### Identity and session conventions (GOZ-0001-IF-01, IF-02, IF-09, IF-11, IF-17, 2026-11-15)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0001 at commit `d2e5c6c` (findings in `docs/specs/001-local-identity/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 2 → 3. These bullets record implemented identity facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants._

- (IF-02) Product pages and API endpoints require a signed-in session by default. Every `/api/v1` endpoint is mapped on the route group in `src/Gozleme.Api/GozlemeApp.cs`, which calls `.RequireAuthorization()`. An endpoint is anonymous only through an explicit `.AllowAnonymous()` that this spec decides and documents. `tests/Gozleme.Api.IntegrationTests/EndpointAuthorizationTests.cs` fails on any endpoint without an authorization decision and pins the exact anonymous list, so update that list deliberately. Map new endpoints on that group, never on `app` directly. Pages are not protected by default: each new page must gate server-side with `getSession()` (`web/src/lib/session.ts`, pattern `web/src/app/page.tsx`; there is no `proxy.ts`). Add an anonymous-rejection test for every new endpoint and page.
- (IF-01) Cross-site request protection has two layers. API: `WebClientHeaderFilter` (`src/Gozleme.Api/Identity/WebClientHeaderFilter.cs`) runs on the whole `/api/v1` group and requires `x-gozleme-client: web` on every unsafe method, so new endpoints get it automatically. Web tier: every new unsafe (non-GET) browser-facing route handler must call `isSameOrigin()` (`web/src/lib/origin.ts`) before `forwardToApi()` (`web/src/lib/api.ts`). `forwardToApi` always adds the API header, so the web-tier check is the browser-facing boundary and is still opt-in per route. The browser reaches the API only through Next.js route handlers (no CORS).
- (IF-17) PostgreSQL outages fail closed for every endpoint through `UseDatabaseUnavailableResponses` (`src/Gozleme.Api/DatabaseUnavailable.cs`), which answers `503 {"error":"unavailable"}`. Do not catch Npgsql connection failures in endpoint code. The web helper maps any API status of 500 or above to 503.
- (IF-09) Cumulative demo:
  - Add a Playwright project `goz-NNNN` that depends on the previous spec's project (`e2e/playwright.config.ts`) and a `specDirs` entry (`e2e/tests/evidence.ts`).
  - CI (`.github/workflows/ci.yml`) and `make demo` with no `SPEC` run the highest-numbered spec that has a Playwright project, so adding the project is enough.
  - Earlier suites write their screenshots to this spec's `evidence/screenshots/regression-goz-NNNN/`.
  - Seeded synthetic accounts are `alice`, `bob` and `lockout@demo.gozleme.test`, with password `GOZLEME_DEMO_PASSWORD`. `alice`'s signed-in browser state is `.demo-tmp/alice-storage-state.json`, subject to the 30-minute idle expiry.
  - The GOZ-0001 suite leaves every `bob` session revoked and `lockout@` locked for 15 minutes, so later suites sign in afresh and never rely on `lockout@`.
  - Extend the idempotent `seed` command (`src/Gozleme.Api/Identity/OperatorCommands.cs`) for new synthetic fixtures. Never seed through migrations.
- (IF-11) Refer to people only by the opaque account id (`ClaimTypes.NameIdentifier`, a UUIDv7), never by email, in telemetry, audit events, URLs and screenshots. Security-relevant events use the `Gozleme.Security.Audit` log category (`src/Gozleme.Api/Identity/SecurityAudit.cs`). Those are log records, bounded by retention and deleted by `make reset`, not a durable audit store.

### Implementation alignment (GOZ-0001-IF-04, IF-05, IF-18, 2026-11-15)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0001 at commit `d2e5c6c` (findings in `docs/specs/001-local-identity/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 2 → 3. These bullets record implemented identity facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants._

- (IF-04) Identity is registered with `AddIdentityCore` and **no** Identity roles (`IdentityServiceCollectionExtensions.cs:38-54`). There is no roles table. Build RBAC on Gözleme's own membership and role tables, and evaluate it from the database per request. Do not use session claims frozen at sign-in, and do not rotate the security stamp, which signs the account out everywhere. A role grant or revocation must take effect on the next request.
- (IF-05) There is no platform administrator. Operator recovery is the shell-only `reset-password`/`unlock` commands, and FR-024 forbids HTTP user listing, password reset and unlock (asserted in `e2e/tests/identity-demo.spec.ts:246-249`). RBAC must not add an HTTP password-reset or unlock surface without human approval. Invariant 10: administrative recovery is not federation authority recovery.

### Organization and tenancy conventions (GOZ-0002-IF-01, IF-05, IF-06, IF-07, IF-08, 2026-11-15)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0002 at commit `f95be4c` (code as demonstrated at `8a9941e`; findings in `docs/specs/002-organizations/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 3 → 4. These bullets record implemented organization facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants._

- (IF-05) Tenants are rows of `gozleme.organizations` (`id` uuid UUIDv7, permanent; `display_name` 1–100 chars, **not unique**; no handle, slug, hierarchy, lifecycle or deletion). Membership is a row in `gozleme.memberships` (PK `organization_id, user_id`). It has no role column, and removal deletes the row. An organization-scoped API is mapped under `/api/v1/organizations/{organizationId}/…` with the ID in the path, never taken implicitly from an "active" organization. Its first step is the membership check `OrganizationAccess.FindMembershipAsync` (`src/Gozleme.Api/Organizations/OrganizationAccess.cs:17-25`), or the GOZ-0003/GOZ-0004 successor of that check, read from the database on every request. A malformed ID, an unknown organization and a non-member all get the same empty `404` with `Cache-Control: no-store` (`OrganizationEndpoints.cs:24,45-49`). `activeOrganizationId` from `GET /api/v1/organizations` (`memberships.selected_at`) is a UI preference only and never authority. Web pages for organization data live under `/organizations/[organizationId]/…`, render the existing "Organization not found" page on 404, and build API paths with `segment()` (`web/src/lib/organizations.ts:44`), which neutralises dot segments. A new tenant-owned table carries `organization_id uuid NOT NULL` with a foreign key to `organizations(id)`.
- (IF-01) Until GOZ-0003 merges, tenant isolation is enforced **by application authorization only**: no RLS policy exists on `organizations`, `memberships` or `invitations` (GOZ-0002 plan, Complexity Tracking). Do not claim RLS protection for any data before GOZ-0003 is merged and verified.
- (IF-07) Telemetry and audit precedent: the span attribute `gozleme.organization.id` (opaque UUID) is set only after membership is confirmed and is never a metric label (`OrganizationTelemetry.cs:17,24,38`). Organization display names, emails and invitation codes never appear in spans, metrics, logs or URLs. Security audit event IDs are allocated per module: identity uses 1001–1010 and organizations use 1101–1108 (`src/Gozleme.Api/Identity/SecurityAudit.cs:13-65`). Give a new module its own range. Audit events remain log records only.
- (IF-08) A new rate-limited endpoint must attach `RateLimitedOperation` metadata (`src/Gozleme.Api/Identity/IdentityServiceCollectionExtensions.cs:119-129,163`; pattern `OrganizationEndpoints.cs:38-41`). Without it, the shared `OnRejected` handler records the rejection as a `gozleme.auth` sign-in or register failure. Rate limiters are in memory and per API instance. Partition by account ID when the endpoint requires a session.
- (IF-06) Demo state after the GOZ-0002 suite:
  - `seed` (`src/Gozleme.Api/Identity/OperatorCommands.cs:27-30,122-150`) now also creates `carol@demo.gozleme.test` and the fixed-ID organization **Seeded Demo Org** (`0193a000-0000-7000-8000-000000000002`). Every run restores its name, exactly alice and carol as members, and no invitations. In the e2e suites these are `DEMO.carol` and `DEMO_ORG` (`e2e/tests/evidence.ts`).
  - The `goz-0002` suite never deletes the organizations it creates. Each run leaves alice in three more run-unique organizations (`Demo Org Alpha/Beta Renamed/Solo NNNNNN`). bob ends with no organization.
  - Later suites therefore use fixed seeded organizations, never assert an exact organization count for alice, and sign in afresh.
  - A demo that needs two tenants with disjoint members adds a second fixed-ID organization to `seed`, for example with bob as its member.
  - Use `recentSpans(service, minutes, operation)` (`e2e/tests/telemetry.ts`) to find spans of a named operation. Poll the metrics scrape for up to 90 s for a counter that is first recorded during the suite, because the SDK exports metrics every 60 s.

### Implementation alignment (GOZ-0002-IF-03, IF-04, IF-09, IF-13, IF-14, IF-15, 2026-11-15)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0002 at commit `f95be4c` (code as demonstrated at `8a9941e`; findings in `docs/specs/002-organizations/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 3 → 4. These bullets record implemented organization facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants._

- (IF-03) **Replace the interim role-neutral rule.** Today any member may rename, invite, list and revoke invitations, list members, remove any other member, and leave. Only the last member is protected (spec FR-015/FR-016; `OrganizationEndpoints.cs`). Every organization-scoped handler calls `OrganizationAccess.FindMembershipAsync` first, so that is the single place to evolve:
  - Keep the membership check first. Non-members still get the identical empty 404.
  - Put the permission check after it. A member who lacks a permission may get `403 {"error":"forbidden"}`, which is already in the contract's error enum (`docs/specs/002-organizations/contracts/organizations-api.openapi.yaml:52`) but is unused today.
  - Turn the last-member guard into a guard that always keeps at least one member able to manage membership. Run it under the same `organizations` row lock (`OrganizationEndpoints.cs:173,190`), including when roles change.
  - Add a bounded `forbidden` failure category to `gozleme.org.operations` (`OrganizationTelemetry.cs:43-51`).
  - Keep `OrgOperation` names as the starting action vocabulary.
- (IF-03) Existing organizations have no roles. `joined_via = 'creator'` and `organizations.created_by` grant nothing by FR-018, and the creator may already have been removed (`OrganizationBoundaryTests.cs`, `Extra_privilege_fields_are_ignored_and_the_creator_has_no_special_standing`). Choose the migration rule that assigns initial roles to existing members, for example every current member becomes a manager or only creators do, during this spec's clarification **with the maintainer**. Do not infer it. The rule must be additive and safe for the Helm `pre-upgrade` migration.
- (IF-04) Removing a member does **not** revoke the open invitations that member created (`OrganizationEndpoints.cs:158-210`), so a removed account can rejoin with a code it minted earlier. Unless GOZ-0002 is corrected first (maintainer decision on GOZ-0002-IF-04), this spec must define and test what happens to a removed member's open invitations, and who may create and revoke invitations.
- (IF-09) Narrow GOZ-0002's no-delegation boundary deliberately:
  - `OrganizationBoundaryTests.No_role_owner_admin_or_permission_column_exists` pins the exact column list of the three organization tables and forbids `role|owner|admin|permission|delegat` (`OrganizationBoundaryTests.cs:32`).
  - `Delegation_routes_do_not_exist` asserts 404/405 for `/members/{user}`, `/members/{user}/role`, `/transfer`, `/owner`, `/admins`, `/roles` and `DELETE` on the organization (`:42-52`).
  - The e2e boundary test forbids role, admin and owner wording on the organization page and allows exactly one combobox (`e2e/tests/organizations-demo.spec.ts:276-277`).
  - Keep ownership transfer, organization deletion and delegated administration absent, because they are post-MVP (R3-08, R3-24).
- (IF-13) No quota or rate limit applies to creating organizations or invitations, and the organization, member and invitation lists are not paged. If invitation creation becomes a permission, say so. Do not add paging unless this spec needs it.
- (IF-14) Assign roles only to existing members, selected by their opaque `userId` from the member list. Do not assign by email address: GOZ-0002 FR-013 forbids any lookup that reveals whether an account exists, and emails are unverified.
- (IF-15) Today any member can mint an invitation and admit a second account they control. Reviewer, approver and manager capabilities must come from explicit role grants, never from membership alone.
