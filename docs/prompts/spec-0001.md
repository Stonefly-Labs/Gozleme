## Starting prompt for `/speckit.specify`

Build **Local identity and session security** as one bounded, runnable, tested vertical slice of the open-source **Gözleme** federated AI capability registry.

**User-visible outcome:** Register, sign in and sign out; protected dashboard rejects anonymous access.

**In scope:** ASP.NET Core Identity local authentication, session and account lifecycle.

**Important boundary:** No external OIDC yet.

Respect the authoritative `docs/architecture/architecture-baseline.md`, `docs/architecture/security-invariants.md`, `docs/decisions/consistency-review.md`, `.gozleme/manifest.yaml`, and spec registry. Use the already installed Spec Kit workflow, its native templates, and confirmed architecture decisions. Do not re-create Spec Kit templates or reinstall Spec Kit. Do not claim unimplemented post-MVP security guarantees.

### Implementation alignment (GOZ-0000-IF-01, IF-02, IF-03, IF-08, IF-10, IF-13, 2026-11-14)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0000 at commit `e7904ad` (findings in `docs/specs/000-repository-bootstrap/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 1 → 2. These bullets record implemented foundation facts and the obligations they create within confirmed architecture; they do not change scope or security invariants._

- (IF-01) GOZ-0000 boundary tests (`tests/Gozleme.Api.IntegrationTests/BootstrapBoundaryTests.cs`, `boundary` test in `e2e/tests/bootstrap-demo.spec.ts`) assert 404 for `POST /api/v1/auth/login`, `GET /api/v1/users` and `/login`, plus no links or 'sign in' text on `/`, and they assert schema `gozleme` has zero tables and only `public."__EFMigrationsHistory"` exists. This spec must narrow only those assertions it legitimately supersedes, keep the remaining ones, and add its own boundary test (no external OIDC); never delete or weaken the suite wholesale.
- (IF-02) Status surfaces are anonymous today: `/health/live`, `/health/ready`, `GET /api/v1/status` and the Next.js same-origin proxy `/api/backend-status` behind the dashboard at `/`. Compose healthchecks use `/health/live` (api) and `/api/backend-status` (web); Helm probes use `/health/live` and `/health/ready`. Keep `/health/*` anonymous. Decide and document explicitly whether the status dashboard and `/api/v1/status` become authenticated; either way keep container healthchecks and the four GOZ-0000 demo scenarios (healthy, database-down degraded, recovery, API unreachable) passing, signing in with a seeded synthetic account if the dashboard becomes protected.
- (IF-02) The browser reaches the API only through Next.js route handlers using server-side `GOZLEME_API_URL` (no CORS; API not browser-exposed). State how the session cookie and anonymous rejection work with this same-origin pattern.
- (IF-08) The demo runner is single-spec: `scripts/demo/run-demo.sh` hard-codes `docs/specs/000-repository-bootstrap` and `--spec GOZ-0000`, the Playwright suite hard-codes its screenshot directory, and CI job `e2e-demo` runs that script. Generalize it to take the spec (for example `make demo SPEC=GOZ-0001`), write `docs/specs/<spec-dir>/evidence/demo-run.json` and `screenshots/`, and keep running prior specs' demo suites cumulatively. No seed mechanism exists; introduce one reusable deterministic synthetic seed path, separate from schema migrations, for demo accounts.
- (IF-10) Persistence facts: single host project `src/Gozleme.Api`; EF Core `GozlemeDbContext` (no entities yet) with migrations in `src/Gozleme.Api/Persistence/Migrations` and history in `public."__EFMigrationsHistory"`; schema `gozleme` exists and is empty. Migrations run only through the one-shot `migrate` command (Compose `migrate` service, Helm `pre-install,pre-upgrade` Job) as `gozleme_migrator`; the API runs as `gozleme_app` with DML only and must never migrate on start-up. Helm `pre-upgrade` runs while previous-release pods still serve, so migrations must stay backward compatible with the prior release. Put identity tables in schema `gozleme` through a new migration. No module layout exists yet; establish only the module(s) this spec needs.
- (IF-13) Deployment conventions: Helm runs containers with `readOnlyRootFilesystem: true` and only `/tmp` (emptyDir) writable; secrets reach pods only through Secrets referenced by name (pattern: `database.existingSecret` with keys `app-connection-string`, `migrator-connection-string`), never chart values. Compose services bind host ports to `127.0.0.1`, take overridable `GOZLEME_*` variables and keep throwaway local defaults in `.env.example`. ASP.NET Core Data Protection keys therefore must not rely on the container-filesystem default; persist them durably for restarts and multiple replicas (for example in the database) and document the choice.
- (IF-03) Role facts: `gozleme_app` is `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS NOINHERIT`; `gozleme_migrator` is `NOSUPERUSER NOBYPASSRLS` and owns the database, schema `gozleme` and every table it creates. The foundation migration sets default privileges so every new `gozleme` table is automatically granted `SELECT, INSERT, UPDATE, DELETE` to `gozleme_app`. No RLS policy or tenant context exists yet. Do not store tenant-owned data in this spec; RLS arrives in GOZ-0003.

### Observability (foundational, GOZ-0000-IF-11, 2026-11-14)

_Provenance: maintainer decision 2026-11-14 that OpenTelemetry is foundational across all work, including browser telemetry; implemented in GOZ-0000 commit `ba6f28c`. Added by the Spec Impact Analyst; Roadmap Steward records the prompt revision. This adds a cross-cutting engineering requirement only; scope, boundaries and security invariants are unchanged._

- Instrument new server code paths with spans and metrics via `GozlemeTelemetry.ActivitySource` / `GozlemeTelemetry.Meter` (name `Gozleme.Api`, registered by `AddGozlemeTelemetry` in `src/Gozleme.Api/Telemetry/GozlemeTelemetry.cs`) and new UI flows via the browser tracer (`web/src/telemetry/browser.ts`); use `gozleme.*` names for custom spans, attributes and metrics, and do not add a second telemetry pipeline.
- Preserve the single browser → web → API → PostgreSQL trace (W3C context; the web tier propagates only to `GOZLEME_API_URL`). Export stays optional (`OTEL_EXPORTER_OTLP_ENDPOINT`), and the collector and Jaeger are never health dependencies.
- Secrets, credentials, tokens, personal data and private or tenant-confidential metadata never enter span names, attributes, events, metric labels or exported logs (invariant 8; GOZ-0000-IF-21). Instrumentation already records `db.query.text`, `http.url`/`http.target` and `user_agent.original`, so keep confidential values out of SQL text (parameters only) and out of URLs. The collector redaction in `deploy/otel/collector.yaml` is defence in depth only. Keep metric label cardinality bounded.
- Assert this spec's key spans and metrics in integration tests (pattern: `tests/Gozleme.Api.IntegrationTests/TelemetryTests.cs`) and in the demo (pattern: `observability` test in `e2e/tests/bootstrap-demo.spec.ts`, Jaeger on `:16686`), including a no-secret check of captured telemetry.
- Spec focus: registration, sign-in and sign-out outcome spans and counters by failure category; never usernames, emails, passwords, cookies or session identifiers. If user identity is recorded at all, use an opaque internal ID and document the choice. Decide authentication, origin checking and rate limiting for the browser ingestion route `web/src/app/api/otel/v1/traces/route.ts` (GOZ-0000-IF-20).
