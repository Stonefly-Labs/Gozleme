## Starting prompt for `/speckit.specify`

Build **S3-compatible artifact adapter** as one bounded, runnable, tested vertical slice of the open-source **Gözleme** federated AI capability registry.

**User-visible outcome:** Run MinIO locally and retrieve verified artifact.

**In scope:** S3-compatible pluggable storage, consistency and lifecycle tests.

**Important boundary:** Local demo must not need AWS.

Respect the authoritative `docs/architecture/architecture-baseline.md`, `docs/architecture/security-invariants.md`, `docs/decisions/consistency-review.md`, `.gozleme/manifest.yaml`, and spec registry. Use the already installed Spec Kit workflow, its native templates, and confirmed architecture decisions. Do not re-create Spec Kit templates or reinstall Spec Kit. Do not claim unimplemented post-MVP security guarantees.

### Required behavior and acceptance tests

- Deliver the outcome above through the cumulative running Next.js/.NET 10/PostgreSQL application; include positive and negative tests suitable for this feature.
- Preserve organization isolation and private visibility, using existing policy/RLS boundaries. Never reveal confidential metadata or secrets through UI, APIs, search indexes, logs, or screenshots.
- Include reproducible seeded fixtures, exact demo commands, expected UI/API observations, and automatic browser-driven demo evidence when feasible.
- Capture meaningful actual screenshots from the working implementation (or API/log evidence if no useful UI view), with PR links and sanitized synthetic data.
- Keep existing demos and smoke tests working. Compose remains runnable without cloud services, hosted embedding providers, or external identity providers by default.
- Document contracts, storage migrations, compatibility and dependency impacts, and any unsupported modes explicitly.
- Implement only this bounded slice. Defer unrelated subfeatures to their scheduled specs rather than constructing speculative frameworks.

### Tenant RLS conventions (GOZ-0003-IF-01, IF-02, IF-09, IF-10, IF-19, 2026-11-15; IF-19 added 2026-11-16)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0003 at commit `9131bda` (code as demonstrated at `424a15e`; findings in `docs/specs/003-tenant-rls/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 4 → 5. These bullets record implemented tenant-RLS facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants. Items that would change them are routed to the maintainer as GOZ-0003 human decisions and are not decided here._

- (IF-01) Once GOZ-0003 has merged (verify on `main`), organization data is protected by the application membership check **and** PostgreSQL row-level security, enabled and **forced** (binding the owner login too) on `organizations`, `memberships` and `invitations`. This supersedes the GOZ-0002-IF-01 "application authorization only" bullet above. The database contract is `docs/specs/003-tenant-rls/contracts/tenant-context.md`, and migration `src/Gozleme.Api/Persistence/Migrations/20261117000000_TenantRls.cs` is the model. A new tenant-owned table must, **in its creating migration**:
  - carry `organization_id uuid NOT NULL` referencing `gozleme.organizations(id)`;
  - `ENABLE` and `FORCE ROW LEVEL SECURITY`, with one policy per command of the shape `CASE WHEN gozleme.rls_internal() THEN true ELSE organization_id IN (SELECT gozleme.account_organizations()) END` (contract §5; `CASE` fixes evaluation order);
  - be added to `TableClassification.TenantOwned` (`src/Gozleme.Api/Persistence/TableClassification.cs`);
  - be added to the cross-tenant matrix in `tests/Gozleme.Api.IntegrationTests/RlsIsolationTests.cs` for both the `app` and `owner` roles (fixtures `Infrastructure/TwoTenants.cs`; leak queries via `GozlemeDatabase.InTransactionAsync` with `GozlemeDatabase.Establish(GozlemeDatabase.SignContext(...))`). `RlsCatalogTests` checks only that a policy exists, not what it admits.
- (IF-01) `RlsCatalogTests` (`RlsCatalog.ViolationsAsync`) fails on an unclassified `gozleme` table, a tenant table without enabled or forced RLS or without a policy, any `SharedPublic` entry (reserved until GOZ-0012), a `SECURITY DEFINER` function in `gozleme` outside the pinned `TableClassification.DefinerHelpers` or a migrator-owned one in any other non-system schema, any view, materialized view or foreign table in `gozleme` (both added at `a81e54e`, GOZ-0003-IF-12), and any `gozleme`/`gozleme_private` function executable by `PUBLIC`. PostgreSQL grants `EXECUTE` to `PUBLIC` on every new function by default, so each new function (trigger functions included) needs `REVOKE EXECUTE … FROM PUBLIC` and an explicit grant to `gozleme_app` if it is called. Do not add `SECURITY DEFINER` functions: inside any migrator-owned definer function `gozleme.rls_internal()` is true, so it bypasses every tenant policy. Extending the pinned list is a security-review item.
- (IF-19) Row policies cannot compare old and new rows. Some tables have identity, tenant-key or lifecycle columns that may change in one direction only: set once, expiry only earlier, never reopened, never moved to another organization. Each such table needs a `BEFORE UPDATE` guard trigger as well as its policies. The model is `gozleme.invitations_guard` in `20261117000000_TenantRls.cs`:
  - Write it as plain `plpgsql`, never `SECURITY DEFINER`, with a fixed `search_path` and `PUBLIC` execute revoked. A trigger function needs no grant to `gozleme_app`.
  - Raise `insufficient_privilege` (`42501`), so that `TenantTransaction` answers the empty 404.
  - Keep `organization_id` immutable on every tenant table.
  - Restrict a policy's bearer-capability branch (such as the invitation code) in its `USING` clause to the open state. A `WITH CHECK` clause sees only the new row.
  - A guard binds every role, the owner and superusers included. A cascaded `ON DELETE SET NULL` fires it, so allow that change explicitly.
  - The catalog check does not pin triggers, so prove each guard with a behavioural test (pattern `TenantContextBoundaryTests.An_invitation_code_cannot_move_reopen_or_extend_its_invitation`).
  - Fully immutable tables still follow GOZ-0000-IF-04 (revoke `UPDATE`/`DELETE`).
- (IF-01) Pins to update with each migration: `LATEST_MIGRATION` in `e2e/tests/bootstrap-demo.spec.ts` (now `/_TenantRls$/`); `BootstrapBoundaryTests.Gozleme_schema_holds_exactly_the_identity_and_organization_tables`; and `BootstrapBoundaryTests.Only_migration_history_and_the_context_key_tables_exist_outside_system_schemas`, which allows only `gozleme_private.context_keys` and `public.__EFMigrationsHistory` outside `gozleme`.
- (IF-02) Request transaction model: `TenantTransaction` (`src/Gozleme.Api/Tenancy/TenantTransaction.cs`) is an endpoint filter attached only to the `/organizations` and `/invitations` route groups (`OrganizationEndpoints.cs:28,42`).
  - Endpoints mapped under `/api/v1/organizations/{organizationId}/…` get it automatically. An endpoint on any other group that touches tenant data must add `.AddEndpointFilter<TenantTransaction>()`; without it every tenant query returns nothing (fail closed).
  - Inside the filter, use the ambient transaction: do not call `BeginTransactionAsync`, do not read tenant data through `IDbContextFactory` or a second `DbContext` (it has no context), and defer audit records with `TenantTransaction.AfterCommit`.
  - The signed context (`v1.<account>.<expires>.<hmac>`, 5 minutes) names the session's account (`ClaimTypes.NameIdentifier`) only, never an organization or role, and every statement re-reads membership. Removal therefore takes effect on the next statement.
  - The filter holds one transaction and one pooled connection for the whole handler. Do not do network or long-running I/O inside it (object storage, embedding providers, federation peers, sandboxes). Split such work into short explicit transactions, each starting with `TenantContext.EstablishAsync(db, signer.Sign(accountId), ct)`. `now()` is the transaction start time, so a token is never re-expired inside one transaction.
  - A principal that is not a signed-in account (a background worker, scheduled job, sync applier or federation peer) touches tenant rows only through a second signed token kind. That token names one organization and a bounded purpose, is verified in the database with the same context key, and is admitted by a new policy branch that the catalog check pins (maintainer decision 2026-11-16, GOZ-0003-IF-04, option A; first consumer GOZ-0015). This is the only sanctioned path: never add a `BYPASSRLS` role, a definer helper or a member service account for it. The first consuming spec designs the token format, the purpose vocabulary, which process signs, and how the catalog pins the branch. Anonymous discovery is not covered by this decision and remains GOZ-0012's question (GOZ-0001-IF-22).
  - Under FORCE, a migration running as the owner without a context sees no tenant rows, so a data migration (`UPDATE`/`DELETE`/`INSERT … SELECT`) on tenant tables silently changes **zero** rows. DDL (`ADD COLUMN … DEFAULT …`) is unaffected. Maintainer decision 2026-11-16 (GOZ-0003-IF-03, option A): a reviewed migration may lift the owner binding **only inside its own transaction**, either with the transaction-local `gozleme.rls_helper` flag or with `ALTER TABLE … NO FORCE ROW LEVEL SECURITY` and then `FORCE` again before commit. A superuser test must assert the per-row results. A migration may **never** disable a guard trigger (IF-19): guarded columns are not backfilled, and a needed change extends the guard in a new migration.
- (IF-09) Telemetry and audit:
  - The `gozleme.tenant.transaction` span (events `gozleme.tenant.context.established` and `gozleme.tenant.context.cleared`) is the parent of module spans and carries no organization ID. `gozleme.organization.id` stays a span attribute, set only after membership is confirmed and never used as a metric label (maintainer decision, GOZ-0003).
  - `gozleme.tenant.denials` has the single label `gozleme.tenant.denial.reason` ∈ {`missing`, `invalid`, `expired`, `refused_write`}. Adding a reason is a contract change.
  - Audit ranges in use: identity 1001–1010, organizations 1101–1108, tenancy 1201–1210 (`src/Gozleme.Api/Identity/SecurityAudit.cs`). Give a new module the next free range, from 1301.
  - The filter answers any SQLSTATE `42501` with the empty 404, counts `refused_write` and writes audit 1202. This includes a plain `permission denied` from a missing grant, so in development a 404 with `refused_write` usually means a missing `GRANT` or policy.
  - An `UPDATE` or `DELETE` whose target the `USING` clause hides changes zero rows without error. EF then raises `DbUpdateConcurrencyException`, answered as 500. Authorization must never rely on RLS errors; the application check runs first.
  - Never log or trace the signed context (prefix `v1.`), the key or an invitation code hash. Pass them only as SQL parameters. The demo scans captured telemetry for them.
- (IF-10) Demo fixtures and configuration after GOZ-0003:
  - `seed` requires `Gozleme__Rls__ContextKey`. It acts only through the signed context of a seeded member (`OperatorCommands.cs` `SeedOrganizationAsync`), never with owner rights. Extend it the same way. A fixed organization that no seeded member belongs to fails with "run make reset".
  - `seed` now also creates `dave@demo.gozleme.test` and **Seeded Partner Org** (`0193a000-0000-7000-8000-000000000003`, member dave only). It is the second tenant, disjoint from Seeded Demo Org. In e2e they are `DEMO.dave` and `PARTNER_ORG` (`e2e/tests/evidence.ts`). This fulfils the GOZ-0002-IF-06 "second fixed-ID organization" suggestion, with dave rather than bob.
  - The `goz-0003` suite (`e2e/tests/tenant-rls-demo.spec.ts`) recreates the API with a mismatched key and then restores it (`composeWithEnv`). It records direct-database evidence as `gozleme_app` and `gozleme_migrator` through `compose()` with tokens signed in Node. Reuse that pattern for database-level isolation evidence.
  - `migrate`, `api` and `seed` need the key: Compose `GOZLEME_CONTEXT_KEY` (throwaway default) and the Helm secret `gozleme-database` key `rls-context-key`. `reset-password` and `unlock` do not need it.

### Implementation alignment (GOZ-0003-IF-02, IF-07, IF-08, 2026-11-15)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0003 at commit `9131bda` (code as demonstrated at `424a15e`; findings in `docs/specs/003-tenant-rls/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 4 → 5. These bullets record implemented tenant-RLS facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants. Items that would change them are routed to the maintainer as GOZ-0003 human decisions and are not decided here._

- (IF-02) Artifact bytes in the filesystem, S3-compatible or Azure Blob store are outside PostgreSQL and outside RLS. Check the tenant row in a short tenant transaction, do the storage or provider I/O outside any transaction, and record the result in a second short transaction that establishes the context again (GOZ-0003-IF-02). Do not hold `TenantTransaction` open across network I/O. Content-addressed deduplication across organizations reveals whether another tenant holds identical bytes: scope dedupe keys per organization, or decide it explicitly.
- (IF-07) `TableClassification.SharedPublic` must stay empty until GOZ-0012 (CR-02). Tables this spec adds are therefore tenant-owned by the publishing organization (private by default; GOZ-0003-IF-01 rules, including FORCE and the isolation matrix) or global account-level identity, or instance reference data in the fourth class (IF-08). GOZ-0012 later defines how public records become visible to other tenants.
- (IF-08) Maintainer decision 2026-11-16 (GOZ-0003-IF-08, option B): a table with no `organization_id` and no tenant content goes in a fourth class (for example `InstanceReference`), never in `GlobalIdentity`. `gozleme_app` gets no DML on it except a pinned read path, and its own `RlsCatalog` rule enforces that. The first spec that needs such a table adds the class, the rule and negative catalog tests, and designs the pinned read path. A table that `gozleme_app` must write at request time does not fit this class.

### Scoped RBAC conventions (GOZ-0004-IF-01, IF-04, IF-06, IF-07, IF-08, IF-09, 2026-11-16)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0004 at commit `7179977` on `feature/goz-0004-scoped-rbac` (findings in `docs/specs/004-scoped-rbac/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 5 → 6. These bullets record implemented role facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants. They apply once GOZ-0004 has merged (verify on `main`). Items that would change them are routed to the maintainer (GOZ-0004-IF-02, IF-13) and are not decided here._

- **Supersedes** the GOZ-0002-IF-05 wording "It has no role column" and the reference to `FindMembershipAsync` as the first step, the GOZ-0003-IF-09 wording "Give a new module the next free range, from 1301", the GOZ-0003-IF-01 pin "`LATEST_MIGRATION` … (now `/_TenantRls$/`)", and the GOZ-0003-IF-10 wording that `seed` acts through "a seeded member" (it now needs a seeded **admin**).
- (IF-01) **Roles.** `gozleme.memberships.roles` (`text[]`, check `ck_memberships_roles`) holds a set of the built-in roles `admin`, `approver`, `member`, `publisher` and `reviewer`. The set is stored distinct and sorted, and `member` is always held. No role implies another, so `admin` does not hold `publisher`, `reviewer` or `approver`. In GOZ-0004, `publisher`, `reviewer` and `approver` permit exactly what `member` permits (maintainer Q4 = A). Users cannot create, rename or edit roles. Adding a built-in role changes committed scope (maintainer Q1 = B) and needs maintainer approval.
- (IF-01) **One decision point.** An organization-scoped endpoint starts with `OrganizationAccess.AuthorizeAsync(db, organizationId, http, action, ct)` (`src/Gozleme.Api/Organizations/OrganizationAccess.cs`).
  - Membership comes first. A null `Access.Membership` gets the identical empty `404`, and no decision is recorded.
  - Then `Access.Allowed == false` gets `403 {"error":"forbidden"}`, and nothing changes.
  - Decide before reading the target resource, so that a `403` never reveals whether a resource exists.
  - Evaluate only through `OrganizationPermissions.Allows(roles, action, resourceType)` (`OrganizationPermissions.cs`); never scatter role checks. GOZ-0018 replaces the evaluation behind this point.
  - A state change that depends on a role re-reads the caller's roles under the per-organization lock and decides again (pattern `LockMembersAsync` in `OrganizationEndpoints.cs`).
- (IF-01) **Contract obligations for a new action.** The action/resource contract is `docs/specs/004-scoped-rbac/contracts/permissions.md` (its location is open, GOZ-0004-IF-13).
  - Add the action to `OrgAction`, and a new resource type to `OrgResource`, in `OrganizationPermissions.cs`. Add the action to the role table, the identical row to the contract's fenced table, and an endpoint → action row.
  - Declare it on the endpoint with `.WithMetadata(new OrgActionAttribute(OrgAction.…))`.
  - `OrganizationPermissionContractTests` fails if the code's table differs from the published one by one character, if a scoped endpoint has no known action, or if an action is declared by no endpoint.
  - Update its pins deliberately: the scoped-endpoint count (`Assert.Equal(9, …)`) and the resource set in `Every_action_has_a_resource_and_a_role_table_row`.
  - The test only recognises routes under `/api/v1/organizations/{organizationId}`. Keep organization-scoped endpoints there (GOZ-0002-IF-05), or extend `IsScoped` in the same change.
  - A spec grants a role only the actions it owns, and never changes the meaning of an existing role silently. Which role holds a new action is a clarification question for that spec.
- (IF-01) **Web.** `GET /api/v1/organizations/{id}` returns the caller's `roles` and `permissions` (action names).
  - Gate UI controls on `permissions`, never on role names. The API stays authoritative.
  - On a `403`, client components route to `forbiddenNoticePath`, which re-renders the page with `?notice=forbidden` and the persistent `forbiddenText` notice (`web/src/lib/client.ts`, `web/src/app/organizations/[organizationId]/page.tsx`).
  - The role list is duplicated as `ROLES` in `web/src/lib/organizations.ts`.
- (IF-08) **Database layer.** Admin-only writes are also enforced in PostgreSQL (maintainer Q3 = B):
  - `organizations_update` and `invitations_insert`/`update`/`delete` admit admins through the non-definer SQL function `gozleme.account_is_admin(org)`.
  - `memberships_insert` gives a creator at most `{admin,member}` and a redeemer exactly `{member}`.
  - The `gozleme.memberships_guard` trigger (`BEFORE INSERT OR UPDATE OR DELETE`) keeps `organization_id`, `user_id`, `joined_at`, `joined_via` and `invitation_id` fixed, and lets `selected_at` change only on the caller's own row. Role changes, removing another member and adding another account all need admin. The guard refuses to remove or demote the last admin, serialized by `gozleme.lock_organization_members(org)`. This closes the GOZ-0003-IF-19 `memberships` gap. `invitation_id` changes only through the `ON DELETE SET NULL` cascade (GOZ-0004-IF-14, fixed before merge).
  - Reads stay member-level in the database; the application alone withholds the invitation list from non-admins.
  - Whether later role-gated writes or reads are also enforced in the database is **open (GOZ-0004-IF-02)**. Do not invent a posture: ask the maintainer during clarification.
  - GOZ-0004 added no `SECURITY DEFINER` function, so `TableClassification.DefinerHelpers` is unchanged.
- (IF-08) **The guard binds everyone.** `memberships_guard` binds every login, the owner and superusers included. Foreign-key cascades pass only through `gozleme.rls_internal() AND pg_trigger_depth() > 1`.
  - A migration therefore cannot change `memberships.roles` or another guarded column. GOZ-0003-IF-03 forbids disabling a guard trigger, so a needed change extends the guard in a new, reviewed migration.
  - An out-of-band SQL repair (in tests or by an operator) needs `SET session_replication_role = replica` as a superuser (pattern `TenantContextBoundaryTests`).
- (IF-04) **Boundary pins.** `OrganizationBoundaryTests` fails if:
  - a table in `gozleme` or `gozleme_private` matches `(polic|grant|role|permission)`;
  - `OrganizationPermissions.Allows` takes anything but `(roles, action, resourceType)`, or `OrganizationAccess.AuthorizeAsync` takes anything but `(db, organizationId, http, action, ct)`;
  - any of these routes under the organization path stops answering `404`: `/roles`, `/policies`, `/permissions`, `/grants`, `/admins`, `/transfer`, `/owner`, and `POST`/`PATCH`/`DELETE /members/{user}/roles`.

  A spec that legitimately adds such a table, parameter or route narrows only the assertion it supersedes, names the change in its tasks, and keeps the rest. GOZ-0004 did this for GOZ-0002 (research R12).
- (IF-06) **Row locks and serialization.** Under RLS, `SELECT … FOR UPDATE`/`FOR SHARE` sees only the rows that the `UPDATE` policy's `USING` clause admits.
  - On `organizations` and `invitations`, a non-admin's row lock therefore finds zero rows and locks nothing, without any error. The same holds for any later table whose `UPDATE` policy is role-restricted.
  - Serialize per-organization membership work with `gozleme.lock_organization_members(org)`, a transaction-scoped advisory lock that is safe to take again.
  - The lock order is advisory lock → organization row → invitation. Redemption takes the organization (`FOR KEY SHARE`) and then the invitation. Keep this order, or prove a new order deadlock-free.
  - Only admins create invitations, and losing admin revokes them (maintainer Q2 = A), so a non-admin never holds an open invitation. A spec that gives `invitation.create` to another role must extend the revocation on role loss.
- (IF-07) **Telemetry and audit.**
  - Every decision emits the span `gozleme.authz.decision` with `gozleme.authz.action`, `gozleme.authz.resource_type` and `gozleme.authz.outcome` (`allow` or `deny`). The counter `gozleme.authz.decisions` carries the same three labels (`AuthorizationTelemetry.cs`). Neither ever carries roles, account IDs, names, emails or codes, and new actions are bounded label values.
  - `gozleme.org.operations` gains the failure categories `forbidden` and `last_admin`, and the operation `member_roles`.
  - A `403` is not a tenant denial, so `gozleme.tenant.denials` is unchanged.
  - Audit events: 1301 `gozleme.audit.authz_denied` (every deny, after commit) and 1302 `gozleme.audit.org_member_roles_changed`. The range 1301–1310 belongs to organization roles, so give a new module the next free range, **from 1401**.
