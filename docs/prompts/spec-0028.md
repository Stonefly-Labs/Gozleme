# GOZ-0028 — Portable signed-resolution-plan lockfiles

**Status:** Initial living `/speckit.specify` prompt; not a completed Spec Kit specification.  
**Release:** MVP · **Phase:** Relationships and deterministic resolution  
**Prerequisites:** GOZ-0027, GOZ-0023

## Starting prompt for `/speckit.specify`

Build **Portable signed-resolution-plan lockfiles** as one bounded, runnable, tested vertical slice of the open-source **Gözleme** federated AI capability registry.

**User-visible outcome:** Export pinned plan, replay and deny after authority change.

**In scope:** Revision/projection digests, dependency edge decisions, revalidation.

**Important boundary:** Lockfile is not perpetual authorization.

Respect the authoritative `docs/architecture/architecture-baseline.md`, `docs/architecture/security-invariants.md`, `docs/decisions/consistency-review.md`, `.gozleme/manifest.yaml`, and spec registry. Use the already installed Spec Kit workflow, its native templates, and confirmed architecture decisions. Do not re-create Spec Kit templates or reinstall Spec Kit. Do not claim unimplemented post-MVP security guarantees.

### Required behavior and acceptance tests

- Deliver the outcome above through the cumulative running Next.js/.NET 10/PostgreSQL application; include positive and negative tests suitable for this feature.
- Preserve organization isolation and private visibility, using existing policy/RLS boundaries. Never reveal confidential metadata or secrets through UI, APIs, search indexes, logs, or screenshots.
- Include reproducible seeded fixtures, exact demo commands, expected UI/API observations, and automatic browser-driven demo evidence when feasible.
- Capture meaningful actual screenshots from the working implementation (or API/log evidence if no useful UI view), with PR links and sanitized synthetic data.
- Keep existing demos and smoke tests working. Compose remains runnable without cloud services, hosted embedding providers, or external identity providers by default.
- Document contracts, storage migrations, compatibility and dependency impacts, and any unsupported modes explicitly.
- Implement only this bounded slice. Defer unrelated subfeatures to their scheduled specs rather than constructing speculative frameworks.

### Observability (foundational, GOZ-0000-IF-11, 2026-11-14)

_Provenance: maintainer decision 2026-11-14 that OpenTelemetry is foundational across all work, including browser telemetry; implemented in GOZ-0000 commit `ba6f28c`. Added by the Spec Impact Analyst; Roadmap Steward records the prompt revision. This adds a cross-cutting engineering requirement only; scope, boundaries and security invariants are unchanged._

- Instrument new server code paths with spans and metrics via `GozlemeTelemetry.ActivitySource` / `GozlemeTelemetry.Meter` (name `Gozleme.Api`, registered by `AddGozlemeTelemetry` in `src/Gozleme.Api/Telemetry/GozlemeTelemetry.cs`) and new UI flows via the browser tracer (`web/src/telemetry/browser.ts`); use `gozleme.*` names for custom spans, attributes and metrics, and do not add a second telemetry pipeline.
- Preserve the single browser → web → API → PostgreSQL trace (W3C context; the web tier propagates only to `GOZLEME_API_URL`). Export stays optional (`OTEL_EXPORTER_OTLP_ENDPOINT`), and the collector and Jaeger are never health dependencies.
- Secrets, credentials, tokens, personal data and private or tenant-confidential metadata never enter span names, attributes, events, metric labels or exported logs (invariant 8; GOZ-0000-IF-21). Instrumentation already records `db.query.text`, `http.url`/`http.target` and `user_agent.original`, so keep confidential values out of SQL text (parameters only) and out of URLs. The collector redaction in `deploy/otel/collector.yaml` is defence in depth only. Keep metric label cardinality bounded.
- Assert this spec's key spans and metrics in integration tests (pattern: `tests/Gozleme.Api.IntegrationTests/TelemetryTests.cs`) and in the demo (pattern: `observability` test in `e2e/tests/bootstrap-demo.spec.ts`, Jaeger on `:16686`), including a no-secret check of captured telemetry.
- Spec focus: lockfile export and replay spans with a revalidation-deny counter.

### Identity and session conventions (GOZ-0001-IF-01, IF-02, IF-09, IF-11, IF-17, 2026-11-15)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0001 at commit `d2e5c6c` (findings in `docs/specs/001-local-identity/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 2 → 3. These bullets record implemented identity facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants._

- (IF-02) Product pages and API endpoints require a signed-in session by default. Every `/api/v1` endpoint is mapped on the route group in `src/Gozleme.Api/GozlemeApp.cs`, which calls `.RequireAuthorization()`. An endpoint is anonymous only through an explicit `.AllowAnonymous()` that this spec decides and documents. `tests/Gozleme.Api.IntegrationTests/EndpointAuthorizationTests.cs` fails on any endpoint without an authorization decision and pins the exact anonymous list, so update that list deliberately. Map new endpoints on that group, never on `app` directly. Pages are not protected by default: each new page must gate server-side with `getSession()` (`web/src/lib/session.ts`, pattern `web/src/app/page.tsx`; there is no `proxy.ts`). Add an anonymous-rejection test for every new endpoint and page.
- (IF-01) Cross-site request protection has two layers. API: `WebClientHeaderFilter` (`src/Gozleme.Api/Identity/WebClientHeaderFilter.cs`) runs on the whole `/api/v1` group and requires `x-gozleme-client: web` on every unsafe method, so new endpoints get it automatically. Web tier: every new unsafe (non-GET) browser-facing route handler must call `isSameOrigin()` (`web/src/lib/origin.ts`) before `forwardToApi()` (`web/src/lib/api.ts`). `forwardToApi` always adds the API header, so the web-tier check is the browser-facing boundary and is still opt-in per route. The browser reaches the API only through Next.js route handlers (no CORS).
- (IF-17) PostgreSQL outages fail closed for every endpoint through `UseDatabaseUnavailableResponses` (`src/Gozleme.Api/DatabaseUnavailable.cs`), which answers `503 {"error":"unavailable"}`. Do not catch Npgsql connection failures in endpoint code. The web helper maps any API status of 500 or above to 503.
- (IF-09) Cumulative demo:
  - Add a Playwright project `goz-NNNN` that depends on the previous spec's project (`e2e/playwright.config.ts`) and a `specDirs` entry (`e2e/tests/evidence.ts`).
  - CI (`.github/workflows/ci.yml`) and `make demo` with no `SPEC` run the highest-numbered spec that has a Playwright project, so adding the project is enough.
  - Earlier suites write their screenshots to this spec's `evidence/screenshots/regression-goz-NNNN/`.
  - Seeded synthetic accounts are `alice`, `bob` and `lockout@demo.gozleme.test`, with password `GOZLEME_DEMO_PASSWORD`. `alice`'s signed-in browser state is `.demo-tmp/alice-storage-state.json`, subject to the 30-minute idle expiry.
  - The GOZ-0001 suite leaves every `bob` session revoked and `lockout@` locked for 15 minutes, so later suites sign in afresh and never rely on `lockout@`.
  - Extend the idempotent `seed` command (`src/Gozleme.Api/Identity/OperatorCommands.cs`) for new synthetic fixtures. Never seed through migrations.
- (IF-11) Refer to people only by the opaque account id (`ClaimTypes.NameIdentifier`, a UUIDv7), never by email, in telemetry, audit events, URLs and screenshots. Security-relevant events use the `Gozleme.Security.Audit` log category (`src/Gozleme.Api/Identity/SecurityAudit.cs`). Those are log records, bounded by retention and deleted by `make reset`, not a durable audit store.

### Organization and tenancy conventions (GOZ-0002-IF-01, IF-05, IF-06, IF-07, IF-08, 2026-11-15)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0002 at commit `f95be4c` (code as demonstrated at `8a9941e`; findings in `docs/specs/002-organizations/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 3 → 4. These bullets record implemented organization facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants._

- (IF-05) Tenants are rows of `gozleme.organizations` (`id` uuid UUIDv7, permanent; `display_name` 1–100 chars, **not unique**; no handle, slug, hierarchy, lifecycle or deletion). Membership is a row in `gozleme.memberships` (PK `organization_id, user_id`). It has no role column, and removal deletes the row. An organization-scoped API is mapped under `/api/v1/organizations/{organizationId}/…` with the ID in the path, never taken implicitly from an "active" organization. Its first step is the membership check `OrganizationAccess.FindMembershipAsync` (`src/Gozleme.Api/Organizations/OrganizationAccess.cs:17-25`), or the GOZ-0003/GOZ-0004 successor of that check, read from the database on every request. A malformed ID, an unknown organization and a non-member all get the same empty `404` with `Cache-Control: no-store` (`OrganizationEndpoints.cs:24,45-49`). `activeOrganizationId` from `GET /api/v1/organizations` (`memberships.selected_at`) is a UI preference only and never authority. Web pages for organization data live under `/organizations/[organizationId]/…`, render the existing "Organization not found" page on 404, and build API paths with `segment()` (`web/src/lib/organizations.ts:44`), which neutralises dot segments. A new tenant-owned table carries `organization_id uuid NOT NULL` with a foreign key to `organizations(id)`.
- (IF-01) Until GOZ-0003 merges, tenant isolation is enforced **by application authorization only**: no RLS policy exists on `organizations`, `memberships` or `invitations` (GOZ-0002 plan, Complexity Tracking). Do not claim RLS protection for any data before GOZ-0003 is merged and verified.
- (IF-07) Telemetry and audit precedent: the span attribute `gozleme.organization.id` (opaque UUID) is set only after membership is confirmed and is never a metric label (`OrganizationTelemetry.cs:17,24,38`). Organization display names, emails and invitation codes never appear in spans, metrics, logs or URLs. Security audit event IDs are allocated per module: identity uses 1001–1010 and organizations use 1101–1108 (`src/Gozleme.Api/Identity/SecurityAudit.cs:13-65`). Give a new module its own range. Audit events remain log records only.
- (IF-08) A new rate-limited endpoint must attach `RateLimitedOperation` metadata (`src/Gozleme.Api/Identity/IdentityServiceCollectionExtensions.cs:119-129,163`; pattern `OrganizationEndpoints.cs:38-41`). Without it, the shared `OnRejected` handler records the rejection as a `gozleme.auth` sign-in or register failure. Rate limiters are in memory and per API instance. Partition by account ID when the endpoint requires a session.
- (IF-06) Demo state after the GOZ-0002 suite:
  - `seed` (`src/Gozleme.Api/Identity/OperatorCommands.cs:27-30,122-150`) now also creates `carol@demo.gozleme.test` and the fixed-ID organization **Seeded Demo Org** (`0193a000-0000-7000-8000-000000000002`). Every run restores its name, exactly alice and carol as members, and no invitations. In the e2e suites these are `DEMO.carol` and `DEMO_ORG` (`e2e/tests/evidence.ts`).
  - The `goz-0002` suite never deletes the organizations it creates. Each run leaves alice in three more run-unique organizations (`Demo Org Alpha/Beta Renamed/Solo NNNNNN`). bob ends with no organization.
  - Later suites therefore use fixed seeded organizations, never assert an exact organization count for alice, and sign in afresh.
  - A demo that needs two tenants with disjoint members adds a second fixed-ID organization to `seed`, for example with bob as its member.
  - Use `recentSpans(service, minutes, operation)` (`e2e/tests/telemetry.ts`) to find spans of a named operation. Poll the metrics scrape for up to 90 s for a counter that is first recorded during the suite, because the SDK exports metrics every 60 s.

### Tenant RLS conventions (GOZ-0003-IF-01, IF-02, IF-09, IF-10, 2026-11-15)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0003 at commit `9131bda` (code as demonstrated at `424a15e`; findings in `docs/specs/003-tenant-rls/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 4 → 5. These bullets record implemented tenant-RLS facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants. Items that would change them are routed to the maintainer as GOZ-0003 human decisions and are not decided here._

- (IF-01) Once GOZ-0003 has merged (verify on `main`), organization data is protected by the application membership check **and** PostgreSQL row-level security, enabled and **forced** (binding the owner login too) on `organizations`, `memberships` and `invitations`. This supersedes the GOZ-0002-IF-01 "application authorization only" bullet above. The database contract is `docs/specs/003-tenant-rls/contracts/tenant-context.md`, and migration `src/Gozleme.Api/Persistence/Migrations/20261117000000_TenantRls.cs` is the model. A new tenant-owned table must, **in its creating migration**:
  - carry `organization_id uuid NOT NULL` referencing `gozleme.organizations(id)`;
  - `ENABLE` and `FORCE ROW LEVEL SECURITY`, with one policy per command of the shape `CASE WHEN gozleme.rls_internal() THEN true ELSE organization_id IN (SELECT gozleme.account_organizations()) END` (contract §5; `CASE` fixes evaluation order);
  - be added to `TableClassification.TenantOwned` (`src/Gozleme.Api/Persistence/TableClassification.cs`);
  - be added to the cross-tenant matrix in `tests/Gozleme.Api.IntegrationTests/RlsIsolationTests.cs` for both the `app` and `owner` roles (fixtures `Infrastructure/TwoTenants.cs`; leak queries via `GozlemeDatabase.InTransactionAsync` with `GozlemeDatabase.Establish(GozlemeDatabase.SignContext(...))`). `RlsCatalogTests` checks only that a policy exists, not what it admits.
- (IF-01) `RlsCatalogTests` (`RlsCatalog.ViolationsAsync`) fails on an unclassified `gozleme` table, a tenant table without enabled or forced RLS or without a policy, any `SharedPublic` entry (reserved until GOZ-0012), a `SECURITY DEFINER` function in `gozleme` outside the pinned `TableClassification.DefinerHelpers`, and any `gozleme`/`gozleme_private` function executable by `PUBLIC`. PostgreSQL grants `EXECUTE` to `PUBLIC` on every new function by default, so each new function (trigger functions included) needs `REVOKE EXECUTE … FROM PUBLIC` and an explicit grant to `gozleme_app` if it is called. Do not add `SECURITY DEFINER` functions: inside any migrator-owned definer function `gozleme.rls_internal()` is true, so it bypasses every tenant policy. Extending the pinned list is a security-review item.
- (IF-01) Pins to update with each migration: `LATEST_MIGRATION` in `e2e/tests/bootstrap-demo.spec.ts` (now `/_TenantRls$/`); `BootstrapBoundaryTests.Gozleme_schema_holds_exactly_the_identity_and_organization_tables`; and `BootstrapBoundaryTests.Only_migration_history_and_the_context_key_tables_exist_outside_system_schemas`, which allows only `gozleme_private.context_keys` and `public.__EFMigrationsHistory` outside `gozleme`.
- (IF-02) Request transaction model: `TenantTransaction` (`src/Gozleme.Api/Tenancy/TenantTransaction.cs`) is an endpoint filter attached only to the `/organizations` and `/invitations` route groups (`OrganizationEndpoints.cs:28,42`).
  - Endpoints mapped under `/api/v1/organizations/{organizationId}/…` get it automatically. An endpoint on any other group that touches tenant data must add `.AddEndpointFilter<TenantTransaction>()`; without it every tenant query returns nothing (fail closed).
  - Inside the filter, use the ambient transaction: do not call `BeginTransactionAsync`, do not read tenant data through `IDbContextFactory` or a second `DbContext` (it has no context), and defer audit records with `TenantTransaction.AfterCommit`.
  - The signed context (`v1.<account>.<expires>.<hmac>`, 5 minutes) names the session's account (`ClaimTypes.NameIdentifier`) only, never an organization or role, and every statement re-reads membership. Removal therefore takes effect on the next statement.
  - The filter holds one transaction and one pooled connection for the whole handler. Do not do network or long-running I/O inside it (object storage, embedding providers, federation peers, sandboxes). Split such work into short explicit transactions, each starting with `TenantContext.EstablishAsync(db, signer.Sign(accountId), ct)`. `now()` is the transaction start time, so a token is never re-expired inside one transaction.
  - There is no tenant context for a principal that is not a signed-in account (background workers, federation peers, scheduled jobs, anonymous callers). How they may touch tenant rows is an open maintainer decision (GOZ-0003-IF-04). Do not invent one in a spec, and never add a `BYPASSRLS` role or a definer helper for it without that decision.
  - Under FORCE, a migration running as the owner without a context sees no tenant rows, so a data migration (`UPDATE`/`DELETE`/`INSERT … SELECT`) on tenant tables silently changes **zero** rows. DDL (`ADD COLUMN … DEFAULT …`) is unaffected. The sanctioned mechanism for cross-tenant backfills is an open maintainer decision (GOZ-0003-IF-03). Until it is decided, keep migrations DDL-only and assert affected row counts as the superuser in tests.
- (IF-09) Telemetry and audit:
  - The `gozleme.tenant.transaction` span (events `gozleme.tenant.context.established` and `gozleme.tenant.context.cleared`) is the parent of module spans and carries no organization ID. `gozleme.organization.id` stays a span attribute, set only after membership is confirmed and never used as a metric label (maintainer decision, GOZ-0003).
  - `gozleme.tenant.denials` has the single label `gozleme.tenant.denial.reason` ∈ {`missing`, `invalid`, `expired`, `refused_write`}. Adding a reason is a contract change.
  - Audit ranges in use: identity 1001–1010, organizations 1101–1108, tenancy 1201–1210 (`src/Gozleme.Api/Identity/SecurityAudit.cs`). Give a new module the next free range, from 1301.
  - The filter answers any SQLSTATE `42501` with the empty 404, counts `refused_write` and writes audit 1202. This includes a plain `permission denied` from a missing grant, so in development a 404 with `refused_write` usually means a missing `GRANT` or policy.
  - An `UPDATE` or `DELETE` whose target the `USING` clause hides changes zero rows without error. EF then raises `DbUpdateConcurrencyException`, answered as 500. Authorization must never rely on RLS errors; the application check runs first.
  - Never log or trace the signed context (prefix `v1.`), the key or an invitation code hash. Pass them only as SQL parameters. The demo scans captured telemetry for them.
- (IF-10) Demo fixtures and configuration after GOZ-0003:
  - `seed` requires `Gozleme__Rls__ContextKey`. It acts only through the signed context of a seeded member (`OperatorCommands.cs` `SeedOrganizationAsync`), never with owner rights. Extend it the same way. A fixed organization that no seeded member belongs to fails with "run make reset".
  - `seed` now also creates `dave@demo.gozleme.test` and **Seeded Partner Org** (`0193a000-0000-7000-8000-000000000003`, member dave only). It is the second tenant, disjoint from Seeded Demo Org. In e2e they are `DEMO.dave` and `PARTNER_ORG` (`e2e/tests/evidence.ts`). This fulfils the GOZ-0002-IF-06 "second fixed-ID organization" suggestion, with dave rather than bob.
  - The `goz-0003` suite (`e2e/tests/tenant-rls-demo.spec.ts`) recreates the API with a mismatched key and then restores it (`composeWithEnv`). It records direct-database evidence as `gozleme_app` and `gozleme_migrator` through `compose()` with tokens signed in Node. Reuse that pattern for database-level isolation evidence.
  - `migrate`, `api` and `seed` need the key: Compose `GOZLEME_CONTEXT_KEY` (throwaway default) and the Helm secret `gozleme-database` key `rls-context-key`. `reset-password` and `unlock` do not need it.
