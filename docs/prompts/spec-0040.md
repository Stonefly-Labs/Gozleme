## Starting prompt for `/speckit.specify`

Build **Email delivery, verification and self-service password reset** as one bounded, runnable, tested vertical slice of the open-source **Gözleme** federated AI capability registry.

**User-visible outcome:** Register and verify an email address from a link received in the local mail catcher. Request a password reset, receive the link, set a new password, and see every earlier session end.

**In scope:**
- Pluggable outbound email delivery: an SMTP adapter, with Mailpit in Compose by default.
- Email verification for local accounts.
- Self-service password reset with single-use, hashed, short-lived tokens.

**Important boundary:** No cloud or hosted email dependency by default, and no change to the sign-in identifier or session model built in GOZ-0001.

Respect the authoritative `docs/architecture/architecture-baseline.md`, `docs/architecture/security-invariants.md`, `docs/decisions/consistency-review.md`, `.gozleme/manifest.yaml`, and spec registry. Use the already installed Spec Kit workflow, its native templates, and confirmed architecture decisions. Do not re-create Spec Kit templates or reinstall Spec Kit. Do not claim unimplemented post-MVP security guarantees.

### Feature-specific requirements (from GOZ-0001 implementation evidence)

- **Delivery.**
  - Use one outbound mail abstraction with an SMTP adapter, configured by `Gozleme:Email:*`.
  - Credentials are secret references (Helm `existingSecret` pattern, GOZ-0000-IF-13), never chart values.
  - Compose adds Mailpit (bound to `127.0.0.1`, throwaway defaults in `.env.example`) as the default sink. No mail leaves the machine by default.
  - Delivery is asynchronous and retry-bounded, and a delivery failure never reveals whether an account exists.
  - The mail server is never a health dependency. If it is reported, add it as an optional `dependencies[]` entry with `required: false` under the status contract v1 rules (GOZ-0000-IF-06).
- **Verification.**
  - Today `users.email_confirmed` is always `false` (`docs/specs/001-local-identity/data-model.md`). The session contract pins `emailVerified` to `const: false` (`docs/specs/001-local-identity/contracts/auth-api.openapi.yaml`), and `RequireConfirmedEmail = false` (`src/Gozleme.Api/Identity/IdentityServiceCollectionExtensions.cs:51`).
  - Revise the auth contract version to allow `true`, with web validator and tests updated together.
  - Decide and document whether sign-in of unverified accounts stays allowed. Existing accounts must keep working after upgrade, because the migration must stay backward compatible for Helm `pre-upgrade`.
  - Only a verified email may later be trusted for invitation matching or account linking (GOZ-0001-IF-05).
- **Password reset.**
  - Tokens are at least 256 bits of randomness, stored **only as a hash**, single-use, short TTL (for example 30 minutes, operator-tunable within safe bounds) and bound to the account's current security stamp.
  - Do not rely on Identity's `DataProtectorTokenProvider` as the at-rest store: the Data Protection key ring is unencrypted in PostgreSQL (research R3).
  - The request endpoint returns the same generic response, status and timing for known, unknown and locked accounts (pattern: `AuthEndpoints.cs` dummy-hash equalisation; research R7).
  - Completing a reset applies the GOZ-0001 password policy (`GozlemePasswordValidator`), clears lockout, and ends every session through the existing `SessionRevoker` (`src/Gozleme.Api/Identity/SessionRevoker.cs`).
  - The operator CLI `reset-password`/`unlock` commands stay as the out-of-band path (invariant 10: account recovery is not federation authority recovery).
- **Abuse resistance.**
  - Add named per-client and per-account rate-limit policies for verification resends and reset requests, extending the single `GlobalLimiter` in `IdentityServiceCollectionExtensions.cs` rather than replacing it.
  - Apply both cross-site request protection layers (`isSameOrigin()` in the web tier, `WebClientHeaderFilter` or its global successor in the API).
  - Tokens appear only in the link's URL fragment or are submitted in a POST body. The landing page must not leak the token through `Referer`, telemetry (`http.url`/`url.path` are recorded, GOZ-0000-IF-21) or browser history: for example, read the token from the URL and replace it before any instrumented fetch.
  - Addresses must be well-formed and length-bounded, and mail headers are never built from raw user input.
- **Privacy and observability.**
  - Spans `gozleme.auth.verify_email`, `gozleme.auth.reset_request` and `gozleme.auth.reset_complete`, with bounded outcome and failure-category labels on `gozleme.auth.attempts`.
  - Security audit events go to `Gozleme.Security.Audit` with the opaque account id only.
  - Never record email addresses, tokens, links or message bodies in telemetry, logs or screenshots. Extend the collector redaction as defence in depth.
- **Registration enumeration.** Decide whether verification-first registration removes the residual duplicate-registration `409` signal accepted in GOZ-0001 research R7, and test the outcome either way.

### Demo acceptance

**Demo walkthrough:**
1. Register a synthetic account and open the verification link from Mailpit. The account shows as verified.
2. Request a password reset for a known and an unknown address, and show that the responses are identical.
3. Complete the reset from the Mailpit link, show that a second browser's session has ended, and show that the used link is refused on replay.

Include a test exercising the stated important boundary: no outbound network access beyond the local Mailpit container, and the sign-in identifier and session model are unchanged.

### Organization and tenancy conventions (GOZ-0002-IF-01, IF-05, IF-06, IF-07, IF-08, 2026-11-15)

_Provenance: added by the post-convergence Spec Impact Analyst for GOZ-0002 at commit `f95be4c` (code as demonstrated at `8a9941e`; findings in `docs/specs/002-organizations/reviews/impact-findings.json`). Roadmap Steward must bump `promptRevision` 1 → 2. These bullets record implemented organization facts and the obligations they create within confirmed architecture; they do not change scope, boundaries, prerequisites or security invariants._

- (IF-05) Tenants are rows of `gozleme.organizations` (`id` uuid UUIDv7, permanent; `display_name` 1–100 chars, **not unique**; no handle, slug, hierarchy, lifecycle or deletion). Membership is a row in `gozleme.memberships` (PK `organization_id, user_id`). It has no role column, and removal deletes the row. An organization-scoped API is mapped under `/api/v1/organizations/{organizationId}/…` with the ID in the path, never taken implicitly from an "active" organization. Its first step is the membership check `OrganizationAccess.FindMembershipAsync` (`src/Gozleme.Api/Organizations/OrganizationAccess.cs:17-25`), or the GOZ-0003/GOZ-0004 successor of that check, read from the database on every request. A malformed ID, an unknown organization and a non-member all get the same empty `404` with `Cache-Control: no-store` (`OrganizationEndpoints.cs:24,45-49`). `activeOrganizationId` from `GET /api/v1/organizations` (`memberships.selected_at`) is a UI preference only and never authority. Web pages for organization data live under `/organizations/[organizationId]/…`, render the existing "Organization not found" page on 404, and build API paths with `segment()` (`web/src/lib/organizations.ts:44`), which neutralises dot segments. A new tenant-owned table carries `organization_id uuid NOT NULL` with a foreign key to `organizations(id)`.
- (IF-01) Until GOZ-0003 merges, tenant isolation is enforced **by application authorization only**: no RLS policy exists on `organizations`, `memberships` or `invitations` (GOZ-0002 plan, Complexity Tracking). Do not claim RLS protection for any data before GOZ-0003 is merged and verified.
- (IF-07) Telemetry and audit precedent: the span attribute `gozleme.organization.id` (opaque UUID) is set only after membership is confirmed and is never a metric label (`OrganizationTelemetry.cs:17,24,38`). Organization display names, emails and invitation codes never appear in spans, metrics, logs or URLs. Security audit event IDs are allocated per module: identity uses 1001–1010 and organizations use 1101–1108 (`src/Gozleme.Api/Identity/SecurityAudit.cs:13-65`). Give a new module its own range. Audit events remain log records only.
- (IF-08) A new rate-limited endpoint must attach `RateLimitedOperation` metadata (`src/Gozleme.Api/Identity/IdentityServiceCollectionExtensions.cs:119-129,163`; pattern `OrganizationEndpoints.cs:38-41`). Without it, the shared `OnRejected` handler records the rejection as a `gozleme.auth` sign-in or register failure. Rate limiters are in memory and per API instance. Partition by account ID when the endpoint requires a session.
- (IF-06) Demo state after the GOZ-0002 suite:
  - `seed` (`src/Gozleme.Api/Identity/OperatorCommands.cs:27-30,122-150`) now also creates `carol@demo.gozleme.test` and the fixed-ID organization **Seeded Demo Org** (`0193a000-0000-7000-8000-000000000002`). Every run restores its name, exactly alice and carol as members, and no invitations. In the e2e suites these are `DEMO.carol` and `DEMO_ORG` (`e2e/tests/evidence.ts`).
  - The `goz-0002` suite never deletes the organizations it creates. Each run leaves alice in three more run-unique organizations (`Demo Org Alpha/Beta Renamed/Solo NNNNNN`). bob ends with no organization.
  - Later suites therefore use fixed seeded organizations, never assert an exact organization count for alice, and sign in afresh.
  - A demo that needs two tenants with disjoint members adds a second fixed-ID organization to `seed`, for example with bob as its member.
  - Use `recentSpans(service, minutes, operation)` (`e2e/tests/telemetry.ts`) to find spans of a named operation. Poll the metrics scrape for up to 90 s for a counter that is first recorded during the suite, because the SDK exports metrics every 60 s.
